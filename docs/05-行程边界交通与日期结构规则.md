# 行程边界交通与日期结构规则

## 1. 目标与范围

系统保留居住地与旅游目的地之间的大交通，用于体现 Agent 对出发地的理解，并形成“从居住地出发—目的地游玩—返回居住地”的完整行程。

当前只支持以下大交通方式：

- 飞机 `flight`
- 高铁 `high_speed_rail`
- 普通铁路 `rail`

当前不支持长途客运、自驾和轮渡的大交通规划。航班取消、延误和临时换乘不做自动监控；发生变化后由用户主动发起局部或整体重排。

新建行程的出发地和目的地必须从“省级区域—城市/地区”行政区划中选择。系统保存城市级高德 `adcode`，只有两个 `adcode` 不同时才规划大交通，不再通过地名字符串判断。具体区县的游玩要求写入旅行偏好。

## 2. 交通角色

交通活动必须区分以下角色：

- `outbound`：从居住地前往旅游目的地的去程，只能位于行程第一天。
- `return`：从旅游目的地返回居住地的返程，只能位于行程最后一天。
- `intercity_transfer`：多城市行程中的城市间转移，当前单城市范围仅预留。
- `local_transfer`：目的地内部交通，不属于大交通边界。

居住地与目的地不同的普通往返行程必须且只能包含一条 `outbound` 和一条 `return`。系统不得把“返回市区”“返回酒店”等目的地内部移动识别成返程。

## 3. 日期结构变化

### 3.1 在末尾增加日期

- `end_date` 延后。
- 原活动日期保持不变。
- 去程保持不变。
- 原返程保持活动 ID 不变并移动到新的最后一天。

### 3.2 在开头增加日期

- `start_date` 提前。
- 原活动的日历日期保持不变，`day_index` 整体后移。
- 原去程保持活动 ID 不变并移动到新的第一天。
- 返程日期保持不变。

### 3.3 在中间插入日期

- 插入点之后的原活动日期和 `day_index` 整体后移。
- `end_date` 延后。
- 去程保持不变。
- 返程随最后一段行程移动到新的最后一天，并保持活动 ID。

### 3.4 删除日期

- 删除首日时，去程移动到新的首日。
- 删除末日时，返程移动到新的末日。
- 删除中间日期时，后续日期前移。
- 若被删除日期包含边界交通，系统必须先迁移边界交通再删除日期。

## 4. 飞机规则

- 去程航班活动位于第一天所有目的地活动之前；返程航班位于最后一天所有目的地活动之后。
- 飞机活动可保存航班号、起飞机场、到达机场、计划起降时间、来源和查询时间。
- 未从真实数据源取得航班号、时间或价格时，不得编造，必须标记为 `estimate` 和“待用户确认”。
- 规划时必须给国内航班预留到机场、值机和安检时间；默认至少提前 120 分钟到达机场。
- 当前不处理航班取消或延误。用户可在行程变化后主动重排。
- 去程卡片的地图定位使用目的地到达机场，返程卡片使用目的地出发机场，便于计算机场与市内活动之间的接驳。

## 5. 铁路规则

- 去程铁路活动位于第一天所有目的地活动之前；返程铁路活动位于最后一天所有目的地活动之后。
- 可保存车次、出发站、到达站、计划时间、来源和查询时间。
- 未查询到真实班次时，只能输出交通建议，不得编造车次和票价，并标记为 `estimate` 和“待用户确认”。
- 去程卡片的地图定位使用目的地到达站，返程卡片使用目的地出发站，便于计算车站与市内活动之间的接驳。

## 6. 硬校验

候选应用前必须满足：

1. `date_start`、`date_end`、每日日期和天数一致。
2. 每日日期连续且唯一，`day_index` 从 1 连续编号。
3. 普通往返行程最多一条去程和一条返程。
4. 去程位于第一天且早于目的地活动；返程位于最后一天且晚于目的地活动。
5. 去程方向为居住地到目的地，返程方向相反。
6. 日期调整时优先移动原边界交通并保持原活动 ID，不得复制一条新的同义交通。
7. 新增过夜日期后必须检查住宿衔接。
8. 大交通的估算信息与真实查询信息必须分开，真实信息必须带来源和查询时间。

## 7. 应用与展示

- 大交通仍显示为活动卡片，但使用边界交通标识，不参与目的地内部路线连线。
- 地图导航只负责机场或车站与目的地活动之间的本地接驳，不用高德市内路线接口模拟跨城航班或铁路线路。
- 用户手动输入的行程标题不随日期增删自动修改。
