## 2. Agent 接口调用前的上下文组装（技术2 必须实现）

Agent **永远只接收一份干净的行程快照**，不接收成员的 pending 编辑草稿。组装逻辑如下：

### 2.1 generate_itinerary（首次生成，最干净）

```
输入：constraints + poi_candidates
组装：无特殊处理，直接调 LLM
```

### 2.2 revise_itinerary / replan_day（多人场景下有 3 种状态）

```
前置条件：前端轮询发现 version 变化 → 拉最新行程快照 S
         同时前端知道自己的"未应用修订"列表（pending_revisions）

Agent 收到的 itinerary_json = 从数据库取出的版本 = 最新已应用快照
                                ↑ 绝不能混入 pending_revisions
```

三种场景：

| 场景 | Agent 收到的 itinerary | 说明 |
|---|---|---|
| 单人编辑（无 pending） | 数据库最新快照，`revisions[]` 全是 applied/rejected | 最常见，Agent 正常工作 |
| 多人但无冲突（A 改第 1 天，B 改第 3 天） | A 和 B 分别调 Agent，各自拿到数据库最新快照。A 应用后 version+1，B 提交时乐观锁失败 → B 拉最新快照重新生成（但 B 改的是第 3 天，A 改的是第 1 天，重新生成 diff 基本不变） | 技术2 实现时：乐观锁失败后自动重试 1 次，用新快照重新调 Agent |
| 真冲突（A 和 B 同时改第 2 天同一条） | A 先应用 → version+1。B 提交时乐观锁失败 → 自动重试 1 次仍失败 → 返回 409 `AGENT_COLLAB_CONFLICT`。前端拉最新快照 + 对比弹窗 → 用户选保留哪版 | 见 §4 冲突解决流程 |

### 2.3 组装伪代码（技术2 参考）

```python
def assemble_context(trip_id: str, base_version: int, agent_input: dict) -> dict:
    """
    在调 Agent 接口前，组装"干净的"输入上下文。
    返回：传给 Agent 的完整 itinerary_json + 校验参数
    """
    trip = db.fetch_trip(trip_id)
    if trip is None:
        raise TripNotFound(trip_id)

    # 乐观锁预检：调用方的 base_version 落后了
    if trip.version != base_version:
        raise CollabConflict(trip.version)

    # 从快照中过滤出已应用的修订——pending/rejected 的不能进 Agent 上下文
    applied_revisions = [r for r in trip.snapshot["revisions"]
                         if r["status"] in ("applied", "rejected")]

    # 组装给 Agent 的干净行程
    itinerary = dict(trip.snapshot)
    itinerary["revisions"] = applied_revisions
    # members/permissions/transfers/weather 等系统填充字段原样保留

    return itinerary
```

**关键约定**：pending_revision（不管是 AI 产出的还是成员手动编辑的未应用草稿）**一律不进 Agent 上下文**。Agent 只看到"已经确定的事实"，pending 的内容让前端自己处理。

## 3. activity_id 稳定性——L1 校验硬规则（多人协同的地基）

**定义**：行程中每个 activity 的 `activity_id` 是不可变锚点。任何人（成员手动 / AI 修订）都不能改变"某个位置上的活动 ID 是什么"，只能改变它的 status（replaced/removed）或修改它的内容。

### 3.1 为什么必须稳定

| 用途 | 举例 |
|---|---|
| 冲突检测 | A 改 act-5 的时间，B 改 act-5 的费用 → 同 ID 检测到真冲突 |
| diff 定位 | diff.path `/days/1/activities/3/title` → 定位到同一个 act-6（假设 day_index=1, activities[3] 是 act-6） |
| 前端 marker 联动 | 地图上的 marker 和 activity_id 绑定，重排时 ID 不变 → marker 不闪动 |
| 差异说明 | "你把 act-7（熊猫基地）换成了 act-12（成都博物馆）"——ID 可追溯 |

### 3.2 L1 校验伪代码（技术2 必须实现，每次 Agent 输出必跑）

```python
def validate_activity_id_stability(old_itinerary: dict, proposed_itinerary: dict,
                                   scope_day_index: int | None = None) -> list[str]:
    """
    返回违反 activity_id 稳定性规则的错误列表。空列表=通过。
    scope_day_index: 如果传了（replan_day 场景），只检查该天；revise_itinerary 场景传 None 检查全行程
    """
    errors = []

    # 收集 old 中所有 activity_id -> 位置映射
    old_activity_locations = {}
    for day in old_itinerary["days"]:
        if scope_day_index is not None and day["day_index"] != scope_day_index:
            continue
        for i, act in enumerate(day["activities"]):
            old_activity_locations[act["activity_id"]] = (day["day_index"], i)

    # 检查 proposed：旧 ID 要么在原位、要么 status=replaced/removed（允许换内容但不换 ID）
    new_activity_ids = set()
    for day in proposed_itinerary["days"]:
        if scope_day_index is not None and day["day_index"] != scope_day_index:
            continue
        for act in day["activities"]:
            aid = act["activity_id"]
            if aid in new_activity_ids:
                errors.append(f"activity_id '{aid}' 重复（同一 proposed 内）")
            new_activity_ids.add(aid)

            # 旧 ID 必须还在原位（或 status=replaced/removed 留在原位）
            if aid in old_activity_locations:
                old_day, old_idx = old_activity_locations[aid]
                # 允许 status 变为 replaced/removed（原地保留）
                # 不允许整个活动被"删除后在别处重新添加"
                if act["status"] == "replaced":
                    pass  # OK: 原地替换
                elif act["status"] == "removed":
                    pass  # OK: 原地移除
                # 正常活动：位置可以变（move），但 ID 不能消失
            else:
                # 新 ID：必须接在现有最大编号之后
                # 校验方式：aid 格式 act-N，N 必须 > old 中所有 N
                pass  # 不在稳定性检查范围，属于"新增"场景

    # 检查：old 中的 ID 不能在 proposed 中完全消失（除非被 replaced/removed）
    for aid in old_activity_locations:
        if scope_day_index is not None:
            old_day, _ = old_activity_locations[aid]
            if old_day != scope_day_index:
                continue  # 不在范围内，跳过
        if aid not in new_activity_ids:
            errors.append(
                f"旧 activity_id '{aid}' 在 proposed 中消失（未标记 replaced/removed）"
            )

    return errors
```

### 3.3 越界 diff 检查（replan_day 专属 L1 校验）

```python
def validate_diff_scope(diff: list, scope_day_index: int) -> list[str]:
    """
    replan_day 场景：diff 只能命中 scope_day_index 的当天活动。
    遍历 diff.path 的 JSON Pointer，解析出 day_index，比对 scope。
    """
    errors = []
    for d in diff:
        path = d["path"]
        # 解析 JSON Pointer /days/<N>/activities/<M>/... → 提取 day_index = N
        # 简化：用正则匹配 /days/(\d+)
        import re
        m = re.match(r"/days/(\d+)", path)
        if m:
            path_day_index = int(m.group(1))
            if path_day_index != scope_day_index:
                errors.append(
                    f"diff 路径 '{path}' 命中 Day{path_day_index}，超出重排范围 Day{scope_day_index}"
                )
    return errors
```

## 4. 冲突检测与解决流程（技术2 + 技术3 配合）

```
时间线
  ──── t0: A 打开行程（version=3）
  ──── t1: B 打开行程（version=3）
  ──── t2: A 调 revise_itinerary（base_version=3）→ Agent 生成 diff → A 点"确认应用"
         → 后端: UPDATE SET version=4 WHERE id=? AND version=3 → ✅ 影响 1 行 → version=4
  ──── t3: B 调 replan_day（base_version=3）→ Agent 基于 version=3 的快照生成 diff
         → B 点"确认应用"
         → 后端: UPDATE SET version=5 WHERE id=? AND version=3 → ❌ 影响 0 行 → 返回 409 AGENT_COLLAB_CONFLICT
  ──── t4: 前端收到 409 → 拉最新行程（version=4）
         → 前端本地保存 B 的 diff（"我的修改"）
         → 前端调 explain_diff(old=B 看到的 version=3 快照, new=数据库 version=4 快照)
         → 前端弹冲突弹窗：
            ┌─────────────────────────────────────┐
            │ 有新的修改！请选择：                 │
            │                                     │
            │ 🟢 保留队友的最新版                  │
            │    "Day1 新增宽窄巷子夜游，预算调整"   │
            │                                     │
            │ 🔵 保留我的修改                      │
            │    "Day2 下午下雨，替换为室内博物馆"   │
            │                                     │
            │ ⚪ 两者合并（分别应用）               │
            └─────────────────────────────────────┘
  ──── t5: 用户选"两者合并"
         → 后端先应用 A 的修订（已在 version=4 里）
         → 再用 version=4 作为 base_version，重新执行 B 的 replan_day
         → 这次 base_version=4 匹配 → 成功 → version=5
```

### 4.1 技术2 实现要点

- 乐观锁失败后**自动重试 1 次**（用最新快照重新调 Agent，适用于"改不同天"的无冲突场景）
- 重试仍失败才返回 409
- 409 响应体必须带 `{"current_version": 5, "conflict_summary": "..."}` 供前端弹窗用
- 冲突弹窗的"两者合并"选项 = 后端按顺序应用两个 revision

## 5. A2 轮询下的版本流转

```
版本号    触发事件
─────────────────────────────────────────────────────────────────
version=1  Agent 首次生成（revisions[0] = create）
version=2  成员 A 手动编辑 act-3 的时间（member_edit）
version=3  AI 修订：预算调整（constraint_change, applied）
version=4  成员 B 手动添加 act-7（member_edit）
           ← 此时 A 的前端轮询到 version=4，比自己本地的 3 新
           ← A 的前端拉最新快照，刷新 UI
version=5  成员 A 和 B 同时改 act-5 → 冲突 → 用户仲裁后合并应用
```

**关键**：`version` 是整数计数器，每次写操作 +1，不回退。轮询间隔 3 秒，前端发现本地 version < 服务器 version 就拉新。

## 6. 与技术2 数据库设计的对齐点

| Schema 字段 | DB 映射 | 技术2 需实现 |
|---|---|---|
| `trip.version` | trip 表 version 列 | 乐观锁 `WHERE version = base_version` |
| `trip.snapshot` | trip 表 JSONB 列（存完整行程快照） | 每次写操作先读快照 → 调 Agent/手动编辑 → 写回 + version+1 |
| `revisions[]` | trip_revisions 表独立存（seq, actor, action, diff JSONB, status, ...） | revisions 历史可追溯；pending_revisions 不入 Agent 上下文 |
| `activity_id` | 仅在 JSONB 快照内（不单独建表） | L1 校验 activity_id 稳定性（技术1 定义的伪代码） |
| `permissions.collab_mode` | trip 表 collab_mode 列 | 固定为 "A2_poll" |

## 7. 已知边界与 future work

| 边界 | 说明 |
|---|---|
| 不支持 CRDT | 多人同时改同一条的冲突靠用户仲裁，系统不自动合并字段级 diff。工业级 CRDT（如 Yjs/Automerge）留作 future work |
| 轮询而非 WebSocket | 3 秒延迟在学生项目可接受；生产环境换 WebSocket/SSE 推送 |
| pending 草稿不入 Agent | 多人同时编辑时，Agent 只看到已应用的事实。成员的草稿由前端本地管理 |
| 离线编辑不处理 | 用户断网时前端可本地编辑，联网后提交若冲突按 §4 流程处理 |
