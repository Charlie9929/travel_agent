# 前端联调需要后端补充或确认

以下内容来自当前 Figma 交互流程与现有 FastAPI 接口的对照。功能范围和业务边界已确定；本文档中列出的其他缺失能力均进入实现范围，可按联调优先级分阶段完成。

## 已确认的项目边界

1. **版本撤销**：不提供历史版本恢复接口，历史修改记录只能查看。前端将“撤销这次调整”改为“查看本次调整”，继续沿用现有版本记录功能。
2. **AI 修订、重排和攻略导入候选的拒绝**：不增加专门的拒绝接口。用户不满意时可以关闭候选弹窗或重新生成。候选不会应用到正式行程，但 AI 调用记录和候选结果可以保留用于排查和审计。该规则不适用于初次行程生成。
3. **真实支付**：明确不支持真实付款和收款。系统只负责记录费用、计算“谁应付给谁多少钱”，结算状态由用户手动标记。页面不出现“立即付款”等可能引起误解的文案。
4. **复杂隐私和记忆能力**：只保存用户主动填写或明确保存的旅行需求，不自动从聊天中提取长期记忆，也不自动将私聊内容发布到群聊。私密需求和共享需求必须明确区分可见范围。
5. **成员加入方式**：同时保留两种方式。
   - 定向添加：owner 搜索已有用户并直接添加为行程成员，不设置等待接受状态。
   - 分享码加入：用户通过有效期内的链接或分享码主动加入行程。

## AI 行程生成与候选应用流程

- 初次生成：行程通过结构校验、业务校验和 POI 回填后直接落库，不经过候选确认流程。
- 行前修订、行中重排：先生成候选行程和差异，用户确认后再应用到正式行程并推进版本。
- 攻略导入：先返回攻略候选条目，用户勾选需要的条目后再应用到行程。
- “拒绝候选不设后端接口”只适用于行前修订、行中重排和攻略导入，不适用于初次生成。

## 大厅讨论与 Agent 规则

- 普通群聊不触发 Agent。用户明确 `@Agent`，或选中某条群消息点击“问问 Agent”时，才调用 Agent 生成回复。
- 当行程发生关键变化时，例如 AI 候选被确认应用、成员手动调整行程、群聊中生成了公开候选、成员加入退出或角色变化，后端自动发送结构化通知。
- 私聊中尚未确认的候选不发布到群聊。私聊候选被用户确认并应用后，只通知行程发生了哪些变化，不披露私聊内容和调整的私密原因。
- Agent 只能读取当前群聊内容、当前行程和用户明确共享的需求，不能自动读取或转述私聊内容。
- 所有行程成员都可以在群聊中询问 Agent；只有 owner 和 editor 可以确认并应用行程调整，viewer 只能查看建议。
- `@Agent` 和“问问 Agent”需要调用 LLM。行程或成员变化通知由后端根据业务事件生成固定结构，通常不再调用 LLM。

## 已确认需要实现的后端能力

- 大厅讨论：消息列表、发送消息、轮询更新、未读数、可见范围，以及 Agent/系统结构化消息。
- Agent 私聊：会话列表、消息历史、发送消息和轮询回复状态。
- 旅行需求：同行者个人需求的保存、查询、代填状态，以及共享摘要的发布和撤回。
- 好友选择：用户搜索、可选用户列表和可添加状态。
- 记忆簿：仅管理用户主动创建或明确保存的记忆，提供列表、详情、纠正、授权范围和删除。
- 记账与分账：账单创建、账单列表、参与人、分摊状态、金额变更和手动结算标记，不涉及真实资金流转。
- 旅行高光：高光记录的创建、查询和编辑。
- 设置：个人资料、Agent 偏好和记忆使用权限。
- 成员信息：成员列表补充昵称、头像、需求完成状态和代填来源。
- 版本展示：为前端提供稳定、可展示的差异字段，不提供版本恢复。
- 行程调整确认：提供候选状态、费用信息、保留项、变更项和应用后的新版本信息；拒绝候选不需要后端接口。
- 错误处理：继续使用统一的 `code`、`msg`、`data` 响应结构。通用错误码与 HTTP 状态码见[《数据库表结构设计与后端 API 接口清单 v1.1》](../%E6%95%B0%E6%8D%AE%E5%BA%93%E8%A1%A8%E7%BB%93%E6%9E%84%E8%AE%BE%E8%AE%A1%E4%B8%8E%E5%90%8E%E7%AB%AF%20API%20%E6%8E%A5%E5%8F%A3%E6%B8%85%E5%8D%95%20v1.1.docx)；Agent 专用错误码见[技术一《02-Agent接口契约》第 4 节](../%E7%AC%AC%E4%B8%80%E5%91%A8%E6%8A%80%E6%9C%AF%E4%B8%80%E5%AF%B9%E6%8E%A5%E6%96%87%E6%A1%A3/02-Agent%E6%8E%A5%E5%8F%A3%E5%A5%91%E7%BA%A6.md)，统一使用 `AGENT_*` 命名。前端只需再整理哪些 `code` 需要展示专门文案。

## 现有接口联调约定

- `/api/v1/trips/{trip_id}/members/invite` 保留为 owner 直接添加已有用户；后端补充可选用户搜索接口，并排除已在行程中的用户。
- `/api/v1/trips/{trip_id}/members` 扩充昵称、头像、需求完成状态和代填来源字段，现有字段保持兼容。
- `/api/v1/trips/{trip_id}/revisions` 保留现有修改记录，后端补充稳定的差异展示结构。
- `/api/v1/ai/replan` 与 `/api/v1/ai/revise` 返回候选状态、候选行程、差异、摘要、费用和基础版本等稳定字段。
- `/api/v1/trips/{trip_id}/ai-runs/{ai_run_id}/apply` 应用后返回新版本号和应用后行程。前端完成应用后再请求一次 `/api/v1/trips/{trip_id}`，以数据库中的最终状态刷新页面。
- `/api/v1/map/poi`、`/api/v1/map/route` 与 `/api/v1/weather` 可直接用于需要实时查询的页面；行程页默认先展示已保存的行程数据，需要路线或天气更新时再调用对应接口。
- 前端统一读取错误响应中的 `code`、`msg`、`data`；普通错误展示 `msg`，需要专门交互的错误再根据 `code` 映射页面状态。
